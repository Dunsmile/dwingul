## Fortune spec coverage and current mismatches

1. **There is no analysis dialog today.** Fortune form submission in `public/js/app.js:159-162` synchronously validates, optionally saves birth data, computes `makeResult`, calls `finish`, immediately writes history, and navigates. Tarot adds a pick screen but card selection directly calls `finish` (`app.js:141`). The implementation needs one explicit state machine: validating → locally interpreting → ready or error. It should identify the work as on-device/local interpretation, avoid fake percentages, cancel stale completion using the existing route token, and allow one result commit only.

2. **Consent is absent from the fortune form.** `profileForm` currently has only an optional unchecked `remember` checkbox. Add a distinct unchecked required use-consent near submit. Copy must name fields (name, birth date, calendar type, optional birth time), purpose (generate the requested fortune/character interpretation), temporary handling (used in this browser for the current result and then included in personal result history only to the extent described), and refusal consequence (cannot generate this result). Link `/privacy/`. The optional remember control must remain separately unchecked.

3. **The proposed “temporary use” wording must match actual storage.** `finish()` always calls `addHistory()` before rendering. `makeResult()` includes `birth`, and `addHistory()` stores the whole result locally and, for configured profiles, uploads the recent history. Therefore birth-derived result objects can contain `r.birth` (pillars/counts and name; inspect exact returned object before release), even when the raw input birthday/time is not visibly rendered. Either sanitize fortune history to exclude raw profile/birth input and document the remaining derived fields, or change consent/policy copy to truthfully say the generated result is retained in local/server personal history (recent 100) until deletion. “Used only for this calculation and immediately discarded” is false under the current path.

4. **Privacy documentation needs source-level alignment.** The policy source is `scripts/build-site.mjs`, not `dist/privacy/index.html`. It currently says birth data are stored only when Remember/Profile Save is selected, but separately says personal result history is retained; it does not explain whether derived pillars/name are embedded in fortune history. Update the source after choosing the sanitization model, rebuild, and verify dist. Also make the form’s retention statement distinguish raw birth-profile storage, derived result history, local history, and server history for configured profiles.

5. **Share payload is currently bounded but needs regression protection.** `share()` sends name/title/display/unit/element/scores/answers and settings, not raw birthday/time or `birth`; shared pages also state that those fields are absent. Preserve an explicit allowlist and test that `birthday`, `time`, `calendar`, pillars, and birth object never enter the request. Avoid spreading result objects into share payloads while refactoring.

6. **Current fortune result hierarchy conflicts with v12.** `resultPage()` puts replay/share buttons inside the large hero before interpretation sections, then inserts the profile-save card before the sections. For four fortune types, render a compact header (small portrait/card, title, optional honest deterministic score/key takeaway), then all interpretation sections/birth explanation, then Home/Again/Share/Compare actions at the bottom. Do not invent a score if `makeResult` has none. Chemistry is nickname-only and is a test-like questionnaire; its consent should describe answers/name rather than birth fields.

7. **Historic results must tolerate new and old shapes.** The history path assigns stored rows directly to `currentResult`. The fortune template needs fallbacks for missing `sections`, `birth`, score, new interpretation fields, or malformed legacy values. Do not assume the analysis dialog existed or rerun computation for historic rows.

8. **Dialog accessibility requirements need concrete acceptance criteria.** Use the existing `<dialog id="dialog">`, give it a labelled heading and live status, move focus to the dialog, provide Close during work, Retry on error, and a disabled “결과 보기” until ready. Closing/route changes must invalidate pending work. Escape should close without committing history. Respect reduced motion and never rely on animation alone for progress. Prevent the global dialog click handler and gameplay modal observer from causing duplicate handlers/state leaks.

9. **“Actual progress/error handling” needs a truthful definition.** Computation is synchronous and local. Use named discrete steps completed around real work (input checked, calendar converted, interpretation prepared) or a busy indicator with no numeric percent. Catch lunar conversion and rendering failures before history commit; show error and retry with the preserved form input.

## Acceptance checks most likely to catch regressions

- Jump screenshots at backing sizes 1080×450 and 640×450 with ground seam at y=390; seeded obstacle screenshots verify visible art bounds against exported collision boxes.
- Sort screenshots at 900×440 and 500×520 in normal and fever state; center queue and exits remain legible.
- Color at late 7×7 with minimum delta 4; inspect computed cell colors and contrast without art filters. Memory at 5/6/7 grids with every target state visible.
- Racing at canvas heights 320, 630, and 1100; projected road edges and horizon align, no decorative prop enters lanes, scenery motion is distance-based.
- Typing at desktop/mobile and stage/boss variants; no background seam at the 384×224 repeat scale, meters and command text remain readable.
- Fortune: consent initially unchecked; submit blocked with actionable error; remember remains independent; Escape/cancel writes no history; ready enables one result action; double click creates one history row; route-away cannot later navigate; error preserves input and retry works.
- Inspect the actual `/api/history` body and localStorage for each fortune with remember off/on and configured/unconfigured profile. Inspect `/api/shares` body to prove raw and derived birth details are excluded. Run only against an in-memory/test server.

## Plan clarifications recommended before implementation

- Define which generated assets are canonical sources, which are production derivatives, and their exact crop/tiling rules. “PNG/WebP” is too open-ended for canvas loaders and build verification.
- State that functional colors, road/lane geometry, hitboxes, and text remain code-rendered above decoration.
- Split “temporary-use consent” from “personal result history retention”; choose and document a single truthful data model.
- Explicitly exempt reaction and other state-color surfaces from scenery replacement.
- Add deterministic asset-unavailable tests: canvas/DOM fallbacks must remain playable even if every new scene file 404s.
